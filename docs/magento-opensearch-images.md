# Magento OpenSearch images

Linux Magento prefers the digest-pinned official OpenSearch image. Before task-state or credential creation, the shared CPU detector reads all reported x86 CPU flags. A proven lack of x86-64-v2 selects the compatibility build; unreadable capabilities stop preparation. ARM64 uses the official image. Selection is checked again before configuration and acquisition.

Both routes use OpenSearch 3.9.0. The compatibility image contains the official **minimal** archive on pinned Debian Bookworm, with a separately pinned Temurin Java 21 runtime. The minimal archive excludes optional plugins, including k-NN and its SIMD native libraries. It provides Magento's ordinary full-text indexing/search, not feature parity with the plugin-bundled image. Core native libraries and the JVM still require live compatibility testing; the CPU flags alone are not proof.

Pins and checksums are in [opensearch-compat.js](../src/opensearch-compat.js): SHA-512 for the official OpenSearch archive, SHA-256 for the Adoptium runtime, immutable digests for Debian, BuildKit and the normal image. Build steps verify Java and OpenSearch execution and retain the archive LICENSE/NOTICE and Java legal files. The image runs as UID/GID 1000, not root. OpenSearch has no published host port; the task's existing isolated Compose search service is unauthenticated and must not be exposed publicly.

No application or database data is adopted from existing containers, volumes or networks. A task-owned temporary builder creates a task-specific image. Acquired image IDs are recorded; reviewed rollback checks those IDs and removes only resources introduced by that task. An interrupted build is not automatically replayed. Missing ownership or identity evidence requires inspection.

Before Magento installation, a reviewed step verifies the OpenSearch version, creates a temporary index, indexes a document, checks the matching result and deletes the probe index. Magento then runs its normal installation, reindex, cron and HTTP checks. Detailed lab history is in the repository's `netbook-docker-validation-status.md`, which is not included in the installed package.

Cold-index writes have a 120-second server timeout and a 150-second client bound, within a bounded verification job. Mutations are not automatically retried. An existing probe index blocks creation; acknowledged indexes are bound to their UUID before cleanup. A lost creation acknowledgment or changed UUID requires inspection, not blind deletion. A timed-out deletion is never automatically issued twice.

The reindex completion marker is written only after successful reindexing. Linux/macOS verification also inspects all configured Magento indexers, including full-text search, rather than accepting the marker alone.
Verification failures identify the fixed check that failed, including in sanitized diagnostics. Final HTTP verification allows 120 seconds, calibrated against successful netbook probes after a confirmed 60-second client timeout. This is separate from the remote execution deadline; a failed check does not authorize replaying installation.

Live validation on 2026-10-21 passed on the Ubuntu 26.04 netbook without x86-64-v2: image build/startup, real index/document/search, Magento 2.4.8-p5 installation, all indexers, cron, cache and HTTP checks. Reviewed rollback completed all five steps and matched saved runtime/path baselines. Interrupted observations were reconciled using existing job results, without replaying installation. This is functional validation, not a performance benchmark or full-host teardown.

The compatibility build is Linux-only. macOS keeps the official Colima route; Windows uses the official image through its existing separate builder. Kubernetes also consumes the shared official-image pin through its separate gateway/catalog, without this Linux CPU fallback. These shared pins are updated, but none of those routes has received live validation of this change.

Sources: [Adobe's Magento/Commerce dependency matrix](https://experienceleague.adobe.com/en/docs/commerce-operations/installation-guide/system-requirements), [OpenSearch maintenance policy](https://opensearch.org/releases/), [official artifacts](https://opensearch.org/artifacts/by-version/), [Java compatibility](https://docs.opensearch.org/latest/install-and-configure/install-opensearch/index/), [Adoptium runtime metadata](https://api.adoptium.net/v3/assets/latest/21/hotspot?architecture=x64&image_type=jre&os=linux&vendor=eclipse). Runtime builds use the fixed links/checksums, never the mutable metadata endpoint.
